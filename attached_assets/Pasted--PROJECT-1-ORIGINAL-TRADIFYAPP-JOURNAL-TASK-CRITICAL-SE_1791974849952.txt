### PRIORITY 1 — Fix critical API authorization vulnerabilities

1. GET /api/user/role

- Require authenticated sessions and server-side authorization.
- Never trust a supplied user ID as proof of identity.
- Return only the fields required by the customer interface.
- Never expose password hashes, MT5 sync tokens, reset tokens, verification tokens, payment-provider secrets or other sensitive internal fields.
- Remove any hard-coded administrator identity or automatic OWNER/PRO privilege assignment.
- Preserve legitimate staff functionality with explicit role checks.

2. POST /api/user/upgrade-dev

- Remove the insecure subscription-upgrade behavior.
- The route must never grant PRO privileges in production.
- Prefer deleting the route if unused.
- If development testing requires it, use an isolated test helper with explicit development-only authorization, never a client-supplied x-user-id alone.
- Confirm that normal paid upgrades occur only through verified, authorized billing logic.

3. GET /api/mt5/status/:userId
4. GET /api/mt5/snapshots/:userId

- Require authentication.
- Enforce ownership checks or narrowly scoped administrative authorization.
- Prevent one customer from accessing another customer's account information.
- Return only necessary account fields.

5. POST /api/mt5/sync

- Require a previously provisioned, valid synchronization credential associated with the intended account/user.
- Reject missing, empty, unknown and mismatched credentials.
- Never enroll a new credential simply because the stored token is empty.
- Preserve compatibility with legitimate existing MT5 synchronization clients where securely possible.
- If correcting the issue requires re-enrollment or changing the MT5 bridge protocol, document it and ask before implementing that migration.
