## CRITICAL DEVELOPMENT RULES

### Rule 1 — Separate source code

Each project must retain its own source code and deployment pipeline.

Do not combine both applications into one repository without explicit approval.

### Rule 2 — Separate production databases

Do not merge databases or directly modify the other product's database.

Future data sharing should use documented, authenticated service APIs and explicit customer authorization where appropriate.

### Rule 3 — Separate environment variables

Do not reuse production database URLs, authentication secrets, payment webhooks, or privileged service credentials across applications.

### Rule 4 — Integration readiness

Whenever implementing a feature that could eventually connect to the other application, consider:
- Stable API contracts.
- Versioned interfaces.
- Consistent identity mapping.
- Correct entitlement boundaries.
- Data privacy.
- Audit logs.
- Migration compatibility.
- Future unified administration.

Do not create a shared integration merely because the two products have similar features.

### Rule 5 — Independent production releases

Do not modify or publish another project's production deployment.

Never change DNS or production configurations without explicit authorization.

### Rule 6 — Shared product design

Use consistent Tradify brand principles where practical.

Keep Journal and Signals recognizable as separate products within the same family.

Do not abruptly redesign functioning user interfaces merely to establish visual consistency.

### Rule 7 — Coordinated integration changes

If a proposed feature requires changes in both projects:

1. Identify the dependency.
2. Write an integration specification.
3. Define which project owns each API and data record.
4. Identify required changes in each repository.
5. Define authentication and authorization requirements.
6. Define backward compatibility requirements.
7. Provide contract tests and rollout order.
8. Wait for approval before performing cross-project integration.

Do not assume that the other Replit Agent has implemented a dependency merely because it appears in the roadmap.
